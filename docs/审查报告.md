# 项目审查报告

> 审查对象：`modbus-diag`（基于 ESP32-S3 的 Modbus 通信诊断工具）
> 审查时间：2026-10-21
> 代码基线：`5cdb868`
> 审查范围：功能完整性（对照论文 FR/NFR）、逻辑正确性、代码质量、交付物完整性

---

## 0. 总体结论

| 维度 | 评级 | 一句话 |
|---|---|---|
| 功能完整性 | **部分完成** | FR1~FR10 协议与诊断主链已闭合，但硬件仅到"可布局"、PCB 未画；扫描范围/端口等参数不可配 |
| 逻辑正确性 | **中上** | 数据通路（帧解析→统计→评分→报告）有 169 项测试兜底；UI 状态机与并发边界仍存在已知盲区 |
| 代码质量 | **中** | 组件化清晰、注释到位；但页面层 2360 行占 37%，渲染与逻辑耦合、magic number 密集 |
| 交付物完整性 | **不完整** | 原理图/PCB 缺失；论文 6.2/6.5/6.8 的实测数据无法由代码复现 |

**结论**：软件主体不是半成品，但**作为毕业设计交付物仍不完整**——缺的是硬件图纸与实物验证数据，不是代码。

### 1.3 缺失（完全没有）

| 项 | 影响 |
|---|---|
| **原理图（.kicad_sch）** | 硬件交付物的核心；目前只有网表 JSON、BOM、布局坐标，评审无法据此判读电路 |

## 2. 逻辑正确性：按严重度

### P0（会导致现场误判或功能失效）

1. **TCP 页状态与真实连接不同步** —— 已修（`8fd3d8d`），但同类模式仍存在风险：
   任何页面缓存"连接/运行"状态而不回读底层，都会出现"界面说正常、实际已断"。
2. **扫描进度事件挤爆事件队列** —— 已修（`47d9eba`）。队列 32 槽 vs 247 次发布，
   会连带丢弃按键事件，导致"扫描中按 BACK 取消"失灵。**这是并发-容量问题，不是功能问题**，
   同类风险点还有：抓包页面每帧 `recent_push` 与队列消费的竞争（单线程消费，暂无问题）。
3. **无 RTC + 日志时间戳为相对时间** —— 现场拿报告无法对应"几点出的故障"。

### P1（数据可信度）

4. **`min_response_us` 哨兵值 `INT32_MAX` 贯穿多处** —— 已在报告/页面做了 `-1` 与 `--` 处理，
   但 `traffic_stats`、`health_metrics`、`report_generator` 三处各自判断，**没有统一的口径函数**；
   新增展示点忘判就会打出 `2147483647`。
5. **被动抓包没有响应时间** —— 设计上正确（显示 `--`），但 `traffic_stats` 的
   `response_time_us` 参数仍接受 0 作为"不计时"，语义靠调用方自觉。
6. **评分模型未考虑"无数据"与"数据极少"** —— 只抓了 1 帧且成功，就会得到 100 分；
   缺少最小样本量门槛（例如 <10 帧时显示"样本不足"）。

### P2（健壮性）

7. **`modbus_master_send_recv` 的 UART 模式仲裁是全局变量**，抓包与主站互斥靠
   `s_uart_mode` 单标志，没有真正的锁；两个任务同时调用会互相踩。
   当前 UI 单线程 + 扫描独立任务，存在**扫描任务与抓包页并发**的窗口。
8. **多处 `fopen/fwrite` 返回值未检查**（日志、报告导出），SPIFFS 满时静默失败。
9. **`device_scan_start` 的 `s_cancel` 是 `volatile bool`，无内存屏障**；
   在双核上理论可能被重排，实践上 xtensa 对 volatile 足够，但属于"靠运气正确"。

## 3. 代码质量

### 3.1 结构

- **优点**：10 个组件职责清晰，依赖单向（`common_config` ← 各组件 ← `display`/`main`）；
  CI 有干净构建；主机测试与固件代码同源（`modbus_rtu.c` 原样编译进测试）。
- **问题**：`display` 2360 行占 37%，其中大量是**页面骨架重复**——
  每个页面都重复 `tft_fill_screen` + `ui_status_bar_draw` + footer 提示 + `s_need_redraw` 三件套。
  新增一页要抄 40 行样板，且 y 坐标全是 magic number（`10/24/38/52/70...`）。

### 3.2 测试

| 层 | 规模 | 覆盖 |
|---|---|---|
| 主机单元 | 169 项 | 协议/TCP/信号/报告/评分/流量 |
| 模拟器自检 | 45 项 | 服务端行为、故障注入 |
| 端到端互通 | 11 项 | 固件帧层 ↔ pymodbus |
| 静态一致性 | 19 项 | 页面注册、事件收发 |
| 硬件自检 | 35 项 | 引脚 ↔ 网表、BOM |
| 布局自检 | 4 类 | 重叠/越界/靠边/完整性 |

- **优点**：测试真的抓到过 bug（响应帧错位、除零、`INT32_MAX` 泄漏、`/data` 死链、事件挤爆队列）。
- **缺口**：**UI 层零测试**。页面逻辑（编辑态、游标、批量写）只能靠静态检查与肉眼，
  这是当前最大的质量盲区。

### 3.3 可维护性

- 引脚、队列深度、超时等分散在 `app_config.h` 与各组件内，**没有 Kconfig**，
  换板子要改代码而非改配置。
- 注释质量高（多数解释了"为什么"而非"是什么"），这是本项目最好的部分。

## 4. 影响分析

| 缺陷 | 对答辩 | 对现场使用 |
|---|---|---|
| 无原理图/PCB | **致命**：电气类毕设的核心交付物缺失，评委必问 | 无法打样，工具停留在"代码可跑" |
| 6.2/6.5/6.8 数据无法复现 | 高：被问到"这些数据怎么测的"难以自证 | — |
| 扫描范围/端口不可配 | 中：显得功能不完整 | 中：窄范围排查要等满 2 分钟 |
| 评分无最小样本门槛 | 中：可能给出"1 帧 100 分"的荒谬结论 | 高：误导判断 |
| UI 无测试 | 中 | 中：改页面容易引入回归 |
| 无 RTC | 低 | 中：报告无法对应真实时间 |
